# Results: four Qt 6.10.3 examples built with moc and with reflect-moc

Every number here comes from a script in this directory run in the
`reflect-moc/gcc16-qt610` image (GCC 16.2, Qt 6.10.3, offscreen QPA, native
arm64). The ported trees are generated by `tools/rqt-migrate` and are not edited by hand.

## Qt-like style (second pass, final)

`rqt-migrate --style qtlike --signals members --macros rqt` leaves the class as Qt wrote
it: `class C : public QObject`, no `bind()`, no forwarding constructor, no opt-in lines,
`signals:` and `slots:` sections, constructors and `emit` call sites untouched. Only
`Q_OBJECT` becomes `RQT_OBJECT`, `Q_PROPERTY(...)` becomes `RQT_PROPERTY(...)` with the
same text, each signal becomes a bodyless data member
`[[=rqt::names("value")]] rqt::signal<void(int)> valueChanged;` and each slot gets
`[[=rqt::slot]]` (enums, class info and `Q_INVOKABLE` still use annotations until the
compat header is used). `Q_INTERFACES` stays as written. All four examples are proven in
this style (build 2 below); the numbers of the first pass further down are kept as the
before-picture.

Migration cost, from each `migration.diff` (lines added and removed over all changed files):

| example | annotation style | qtlike style | auto constructs, annotation | auto constructs, qtlike |
|---|---|---|---|---|
| mandelbrot | +20 -7 (3 files) | +12 -2 (2 files) | 11 | 4 |
| sliders | +33 -15 (5 files) | +20 -9 (3 files) | 22 | 12 |
| queuedcustomtype | +32 -14 (5 files) | +17 -6 (3 files) | 21 | 9 |
| birthdayparty | +120 -79 (10 files) | +73 -38 (7 files) | 90 | 45 |

Build and output, qtlike ports, each built from a snapshot of committed code
(`git archive HEAD include examples/qt`, so later library edits cannot change a run).
`examples/qt/check.sh ported` and `check_no_moc.sh`; `-Wall -Wextra`, `-j2`.

| example | build 1: before the owner anchor | build 2: with the owner anchor and the signal-receiver fix |
|---|---|---|
| mandelbrot | 0 moc lines, identical (11 lines), 5 warnings | 0 moc lines, identical (11 lines), 0 warnings |
| queuedcustomtype | 0 moc lines, identical (15 lines), 5 warnings | 0 moc lines, identical (15 lines), 0 warnings |
| birthdayparty | 0 moc lines, identical (54 lines), 42 warnings | 0 moc lines, identical (54 lines), 0 warnings |
| sliders | build fails | 0 moc lines, identical (27 lines), 0 warnings |

- **Build 1 warnings** were all `-Wsubobject-linkage`: "'C' has a field
  'rqt::signal<void(...)> C::name' whose type has internal linkage", one per data-member
  signal per translation unit that includes the class. The library change that gave
  `rqt::signal` one external-linkage type (an owner anchor in `RQT_OBJECT`) removed them
  all: 0 in build 2. The tool did nothing about them.
- **sliders in build 1** failed on `connect(dial, &QDial::valueChanged, this,
  &SlidersGroup::valueChanged);`, a signal used as the receiver of a pointer-to-member
  connect (`qobjectdefs_impl.h:547:70: error: invalid conversion from 'QObject*' to
  'SlidersGroup*'`). Build 2 compiles the same, unchanged source line, once a data-member
  signal can be that receiver in the library.
- **RQT_OBJECT first.** With the owner anchor every class that has a data-member signal needs
  `RQT_OBJECT` before its first signal. The tool replaces `Q_OBJECT` in place and now reports
  a class whose signal is declared before that line (`signal before RQT_OBJECT`, unit-tested);
  none of the four examples has one.
- An earlier rebuild against the shared working tree broke on library edits in flight, which
  is why the builds use a snapshot. The ports in build 2 were generated by the committed tool.
- Build time and binary size of the Qt-like ports are in the next section; the "Build time"
  and "Size" tables after it are the annotation style's.

### Qt-like style: build time, size, object growth

`examples/qt/measure.sh` on a snapshot of the committed tree: each variant (moc original,
Qt-like port) built from scratch three times (configure plus build, Release, `-j2`, wall
clock; each build covers the app and its harness). Seconds, median with minimum to maximum.

| example | moc build | Qt-like build | ratio of medians |
|---|---|---|---|
| mandelbrot | 29.2 (17.9 to 101.5) | 109.8 (101.5 to 176.2) | 3.8 |
| sliders | 31.1 (23.8 to 44.4) | 34.0 (31.4 to 50.4) | 1.09 |

dominated by that load (mandelbrot's moc build ranged 17.9 s to 101.5 s on its own).

Bytes from `wc -c` on the linked executable and on `strip -o` of it. Stripped, the Qt-like

Object growth from the owner anchor (a probe compiled with GCC 16.2 for aarch64,
`sizeof` of an `RQT_OBJECT` class): a plain `QObject` subclass is 16 bytes, `RQT_OBJECT`
with no signal 24, with one signal 32, with three signals 48. That is 8 bytes for the hidden
first member plus 8 bytes per data-member signal.

Everything below is the first pass, the **annotation/mixin syntax**
(`rqt-migrate --style annotations`): `class C : public rqt::Object<QObject>`, `bind();` in
constructors, `[[=rqt::...]]` annotations in place of the Q_ macros, and the tier B opt-in
lines. It is the before-picture.

## Verdict

| example | built without moc (a) | observable output identical (b) | warning-free (c) |
|---|---|---|---|
| mandelbrot | yes | yes, 11 lines | yes |
| sliders | yes | yes, 27 lines | yes |
| queuedcustomtype | yes | yes, 15 lines | yes |
| birthdayparty | yes | yes, 54 lines | yes |

- **(a)** `examples/qt/check_no_moc.sh` rebuilds each ported example from scratch with
  the full command lines and fails on any moc invocation (`libexec/moc`, `AUTOMOC`
  steps, `mocs_compilation.cpp`, `moc_*.cpp`, or a generated moc file in the build
  tree). All four pass. The same script with `RQT_VARIANT=original` is the positive
  control: it fires on all four originals (4 to 6 moc log lines, 6 to 10 generated moc files each).
- **(b)** `examples/qt/check.sh ported` runs each harness (the example's classes
  driven headless, printing every class's meta-object and a trace of its signals
  and state) and diffs it with `expected_output.txt`, recorded from the moc build.
  No line is normalised: the harnesses leave out what is nondeterministic (render
  timings, the party's start time, random block positions) instead of masking it
  after the fact.
- **(c)** built with `-Wall -Wextra`; the build log has 0 `warning:` lines for all four.

### birthdayparty: property order

moc orders a class's properties by their `Q_PROPERTY` lines; reflect-moc orders them
by the position of the annotated getter in the class. In `BirthdayParty` the lines
read host, guests, announcement but the getters are declared host, announcement,
guests, so the first port differed in two swapped lines of the meta-object dump.
The library gained an explicit position, `rqt::property{.index = N}`, and the tool
emits it for every property of a class whose `Q_PROPERTY` order differs from its
declaration order (only `BirthdayParty` here). With it the harness output is
identical, all 54 lines.

| example | files changed | lines | auto constructs | partial | manual | unmigrated |

A construct is one rewrite the tool reports: a `Q_OBJECT`, a signal, a slot, a

### What each port needed by hand

Nothing in the ported sources: they are the tool's output byte for byte. The honest
part is what the migration adds that moc did not need, all of it generated:

- **`bind();`** as the first statement of every constructor body, because a class is
  bound to its meta-object by its most derived constructor body. A class with only
  inherited constructors (`using Base::Base;`) gets a forwarding constructor template
  instead (birthdayparty: six classes), since an inherited constructor has no body.
- **The tier B opt-in** (`static QMetaObject const &staticMetaObject;` and
  `RQT_STATIC_META_OBJECT(T);`) for the classes the sources need it for: used with
  `qobject_cast`, `&T::signal` connects, `T::staticMetaObject`, registered with QML,
  or used as a pointer type in a property or method. Detected from the sources;
  mandelbrot 1 class, sliders 2, queuedcustomtype 2, birthdayparty 7.
- **QML registration** (birthdayparty): with moc gone, qmltyperegistrar has no
  metatypes JSON, so the tool generates `rqt_qml_types.hpp` (seven `qmlRegister*`
  calls, from moc's class info), calls it before each QML engine and adds
  `NO_GENERATE_QMLTYPES` to the two `qt_add_qml_module` targets.
- **`Q_INTERFACES(QQmlPropertyValueSource)`** becomes a generated `qt_metacast`
  override.
- **A class derived from another migrated class keeps its base** (`Boy : Person`),
  because `rqt::Object<Person>` would repeat `rqt::object_tag`.
- **CMake**: `CMAKE_AUTOMOC OFF`, C++26 without extensions, `-freflection`,
  `QT_NO_KEYWORDS`, and the include path to the header-only library.

Library gaps found while doing this, all fixed by rqt-qt before these numbers were
taken: private slots and invokables, enums in a namespace as parameter types (`Qt::Orientation`),
member templates and constructor templates in a reflected class, the property flags
FINAL, CONSTANT, REQUIRED and NAME, pointer-typed properties and arguments, and a
forwarding constructor that made QML take the class for a value type, and the property
order above. No gap is open.

## Build time (annotation style, first pass)

The timings were taken before `.index` existed; the only change since is `.index = N`
on three properties of one class in birthdayparty, which does not change what is compiled
in a way that matters here (a re-run of the build after it took 102 s at -j2).

`examples/qt/measure.sh`: each variant is built from scratch (configure plus build,
Release, `-j2`, wall clock) three times. Each build covers the example's app and its
harness, so every translation unit is compiled twice. Seconds; the median is
reported with the minimum and maximum.

| example | moc build, median (min to max) | reflect-moc build, median (min to max) | ratio |
|---|---|---|---|
| mandelbrot | 20.2 (18.8 to 23.7) | 29.3 (28.7 to 31.3) | 1.45 |
| sliders | 55.9 (47.4 to 57.2) | 46.9 (45.9 to 49.0) | 0.84 |
| queuedcustomtype | 54.1 (49.9 to 59.2) | 63.8 (61.1 to 66.5) | 1.18 |
| birthdayparty | 65.4 (60.3 to 68.9) | 105.8 (78.1 to 132.0) | 1.62 |

**Caveat, read before using these numbers.** The Mac was heavily loaded and shared with
other builds while this ran (8 cores; load average 2.2 at the start, 4 to 11 during
the run, 6.0 at the end), and the per-run load is in the script's output. The spread is
large, birthdayparty's ported runs especially (78.1 s to 132.0 s, rising with load), and
the order of the runs (originals before ported for each example) is not randomised.
Read the ratios as "reflect-moc is somewhere between a bit faster and clearly slower
to compile on these examples", not as a measurement of a ratio. Sliders is the
only example where the ported build was faster in all three runs.

## How to reproduce

```sh
docker run --rm -v "$PWD":/src -w /src reflect-moc/gcc16-qt610 examples/qt/migrate.sh
docker run --rm -v "$PWD":/src -w /src reflect-moc/gcc16-qt610 examples/qt/check.sh ported
docker run --rm -v "$PWD":/src -w /src reflect-moc/gcc16-qt610 examples/qt/check_no_moc.sh
docker run --rm -e RQT_VARIANT=original -v "$PWD":/src -w /src reflect-moc/gcc16-qt610 examples/qt/check_no_moc.sh   # must FAIL
docker run --rm -v "$PWD":/src -w /src reflect-moc/gcc16-qt610 examples/qt/measure.sh
```
